# 实测报告：「到点统一停止播放」新思路可行性

日期：2026-11-14 · 机器：macOS 15.8.3 (24H241) / **Intel i7-8700B** / 工程 `view-timer`

> 环境更正：任务书称本机是「Apple Silicon Mac mini」，实测是 **Intel i7-8700B**（Mac mini 2018）。  
> 两者对 MediaRemote 行为无本质差异，但记录在此，避免后续排障时被前提误导。



---

## 一、一句话结论

**新思路在技术上成立，但对 v1 的主渠道（腾讯视频客户端）无效。**

MediaRemote 的「只发 pause 不读」确实能工作——前提是**目标 App 主动注册了 Now Playing**。  
腾讯视频**不注册**，所以这条命令对它等于对着空气说话。v1 仍然必须走「激活窗口 + 空格」，  
也就仍然需要辅助功能权限。**不能按新思路做架构收敛。**

---

## 二、关键实验：为什么上一轮会误判「SendCommand 是空转」

上一轮的记录是「返回 true 但什么都不做」。这个结论**是错的**，而且错因正是任务书第 5 条说的那个坑。

我用一个自建的假播放器（注册 NowPlayingInfo + 监听 MPRemoteCommandCenter）做双对照：

| 实验   | 做法                                               | 结果                               |
| ---- | ------------------------------------------------ | -------------------------------- |
| 对照 A | 发 `MRMediaRemoteSendCommand(kMRPause)` 后**立即退出** | 命令**凭空消失**，播放器一声没吭               |
| 对照 B | 同样发送，但**转 1.5 秒 runloop** 再退出                    | 播放器**准点收到 pause**，音频 2 秒内从输出列表消失 |

→ 结论：**异步 XPC，发送后进程必须活够时间**。上一轮「返回 true 却没效果」多半就是发完立刻退进程。

补充实测（同一机制）：

- `GetNowPlayingApplicationPID` 返回 **0**、`GetNowPlayingInfo` 返回 **null** —— 即使对自己刚注册的播放器也读不到。  
  **「读」确实被 15.4+ 封死，但「写」没被封。** 任务书第 2 条的猜测被证实。
- **单槽位坐实**：假播放器暂停后仍占着槽位，我发 `play` 命令，它立刻重新出声；同一时刻腾讯视频在旁边播着，  
  根本没被选中。这与任务书第 1 条、第 5 条一致。

## 三、腾讯视频到底配不配合（全项目最大未知数，已解）

测试条件：清掉占用槽位的假播放器，确保无干扰；腾讯视频正在输出音频（CoreAudio 实测）。

| 步骤                                  | 结果                   |
| ----------------------------------- | -------------------- |
| 发 `kMRPause`，转 1.5s runloop         | 返回 true              |
| 之后逐秒观察 16 秒                         | **音频 16 秒持续输出，毫无变化** |
| 换发 `kMRTogglePlayPause` / `kMRPlay` | 同样无反应                |

→ **腾讯视频不响应系统 pause 命令**。原因：它没有把播放会话注册进 Now Playing，  
既不是「收到了但拒绝」，而是「根本不在候选名单里」。  
（旁证：槽位被假播放器占着时，我发的命令全部被假播放器吃掉，腾讯视频连被投递的资格都没有。）

## 五、对架构的影响

### 不能做的

把 v1 收敛成「定时器 + Core Audio + 发 pause + 锁屏」——**不成立**，pause 对腾讯视频无效。

### 反而得到的三个实际收益

1. **可以砍掉两条无效降级链**：AX 按暂停（拿不到控件）、媒体键（大概率无效）都是死路。  
   现在最坏情况要 14s + 14s 空等 28 秒才到「退出 App」；砍掉后失败路径直接缩短。  
   正常情况仍是「激活 + 空格 → 等音频释放」这一条。
2. **v2（Edge 网页版）可以直接用 MediaRemote pause**，不需要浏览器扩展、不需要 Native Messaging。  
   机制已用假播放器证明可用。这是本次实测对 v2 的真实红利。
3. **历史记录里的错误结论必须改掉**，否则下一轮还会照着「MediaRemote 全废」去设计，或者反过来  
   乐观地以为发 pause 就能收工。需要修正的地方：
   - `Sources/AudioActivity.swift` 头部注释（「SendCommand 也变成空转」）
   - `Sources/StopExecutor.swift` 类注释（第 3 级媒体键的描述）
   - `README.md` 「实测结论」第 1 条
   - `.workbuddy/memory/2026-11-14.md` 的技术结论 1

### 补充实测（回答上一轮遗留的「媒体键未测」）

用假播放器 + view-timer 自身的发键能力测了一次：

- `辅助功能 = true` —— 证书签名方案确实让授权在重编译后仍然有效。

## 七、剩余风险

- 空格方案依赖**辅助功能权限**，且客户端在全屏 Space 时需要先等前台切换完成，否则按键打空（历史已踩）。
- 空格是 toggle 语义：若客户端其实已暂停而信号滞后，再发一次会把视频**重新放起来**。现有代码靠「先确认在播」规避，但该确认本身有约 1.5 秒的滞后窗口。
- 腾讯视频升级后若开始注册 Now Playing，pause 路线会突然变得可用——届时可再简化为「发 pause → 只做音频复核」。
- 本次未验证：客户端在「全屏 Space」「画中画」「投屏」等状态下的空格响应。

# 八、v1.1：改为「统一停止」（2026-11-14 21:10）

## 起因

用户拿 Edge 播视频验收，发现到点毫无反应，问「空格发了吗」。
答案是**一个键都没发**：原来的 `StopExecutor` 只盯着 `com.tencent.tenvideo` 的音频输出，
Edge 在播时它判定「客户端已暂停」→ 为防 toggle 误触重播 → 主动跳过所有按键。
它**看不见屏幕上有别的东西在播**。这不是 bug，是最初「v1 只做腾讯视频客户端」的范围所致。

用户确认两件事后决定扩范围：
1. 20:58 我发的那次系统 pause，**确实是它把 Edge 视频停住的**（用户没有手动暂停）。
2. 同意现在就加浏览器支持。

## 新发现：浏览器侧无法复核

| 事实 | 影响 |
|---|---|
| Edge 的音频挂在 `Microsoft Edge Helper (Aperitif)` 上 | 不是主进程，映射麻烦 |
| 该 helper 的 `piro` 标志**永久卡在 1** | 暂停后连续观察 12 秒仍为 1，**判断不了在不在播** |
| 同一原因，「等音频静默」这个验收手段对浏览器也失效 | **验收不了停没停** |
| `pause` 是幂等的（空格/媒体键是 toggle） | 所以浏览器侧可以「闭着眼睛发」，这是唯一能这么干的前提 |

## 另一条实现细节：不需要 runloop

之前的对照实验只证明了「发送后进程必须活一会儿」，没区分是 runloop 还是单纯存活。
补做 `sendsleep`（只 `usleep(1.5)`、不转 runloop）→ 播放器**照样收到 pause**。
⇒ 实现里用 `usleep(1.0)` 即可，不必在主线程切 runloop，后台队列安全。

## 新流程（Sources/StopExecutor.swift）

```
0. 列出当前发声进程（日志可见，便于确认到底在停谁）
1. 系统 pause —— 无条件发，幂等，覆盖浏览器/QuickTime/音乐
2. 腾讯视频在播 → 激活（失败重试一次）→ 空格 → 等静默 14s
3. 仍在播 → 媒体键（与键盘焦点无关）
4. 仍在播且已开启 → 退出客户端（丢进度，显式告警）
5. 确认停止后才锁屏
```

## 验收

| 项 | 结果 |
|---|---|
| 编译 | ✅ |
| 安装 | ✅ 证书签名 |
| App 进程内的系统暂停是否能送达 | ✅ 用假播放器做接收端，`VT_SELFTEST` 跑真实 App，假播放器在 5.70s 收到 `pause` |
| 发声进程诊断 | ✅ 日志正确输出 `当前发声进程：FakePlayer(78557)` |
| 无播放源时 | ✅ `系统暂停（执行时无音频输出）`，`stopped=true`，未误发按键 |
| Edge 端到端 | ⏳ 待测（需在 Edge 里播视频 + 面板设 1 分钟） |

## 仍然存在的诚实边界

- 浏览器通道**无法验证**是否真的停了。日志会标注「无法复核」，这是当前技术条件下的最好结果。
- 「播完当前再停」**只对腾讯视频有效**，对浏览器无效（音频标志不回落）。
- 若将来发现某浏览器不响应 pause，只能降级到「激活 + 空格」或「⌘W 关标签」，
  后者会丢页面状态，默认不做。

# 追加：关闭浏览器标签页（2026-11-14 21:30）

需求：给浏览器再加一级兜底 —— 发 ⌘W 关掉当前标签页。**做成可选开关，默认关闭**，
与「兜底：结束腾讯视频进程」同级。

## 先补一刀：读取接口彻底封死

之前只测了 `GetNowPlayingInfo` / `GetNowPlayingApplicationPID` 返回空。这次把另外两个也试了：

| 符号 | 有回调 | 返回值（有播放源时） |
|---|---|---|
| `MRMediaRemoteGetNowPlayingApplicationIsPlaying` | ✅ 不超时 | **0**（假播放器明明在播） |
| `MRMediaRemoteGetNowPlayingClients` | ✅ 不超时 | **空数组** |

结论：不是「回调超时」而是「返回空数据」——读封锁比预想的更彻底，
所以**没有任何办法判断浏览器是否还在播**。这是第 5 级只能「无条件执行」的根本原因。

## 实测记录

| 项 | 结果 |
|---|---|
| ⌘W 键盘事件是否真的能关窗口 | ✅ TextEdit 窗口数 1 → 0 |
| 真实播放器是否响应 ⌘W | ✅ QuickTime 窗口数 1 → 0 |
| 假浏览器（只出声、不注册 Now Playing）全链路 | ✅ 识别 → 前台判断 → ⌘W → 窗口关闭、进程退出、音频消失 |
| 浏览器**不在前台**时 | ✅ 跳过，不抢焦点，窗口数不变，前台应用不变 |
| 结果文案 | ✅ `系统暂停（浏览器 / 其它播放器） + 关闭浏览器标签页`，并标「无法复核」 |

## 两个必须记住的坑

1. **`Arioso/Aperitif` 残影会骗人**。实测中 Edge 明明没在放视频，
   `Microsoft Edge Helper (Aperitif)` 仍报告「正在输出音频」。如果按这个信号去
   **激活 Edge 再发 ⌘W**，就会把用户正在用的窗口拽到前台、再关掉一个无关标签。
   （第一次实现就是这么写的，测试时侥幸因「激活失败」躲过一次误关。）
   → 最终改为：**只处理已经在前台的浏览器，绝不抢焦点**。

2. **⌘W 是「菜单项快捷键」，不是系统级快捷键**。没有菜单栏（File > Close）的 App
   根本不响应它。测试用的假浏览器一开始没建菜单，表现就是「命令发了但什么都没发生」——
   差点被误判成「⌘W 投递失败」。真实浏览器都有菜单，不受影响。

## 诚实边界

- **无法区分**「pause 无效、视频还在放」和「pause 已生效、只是标志卡在 1」。
  两者在音频信号上完全一样，所以开启后**必然会把已经暂停的标签也关掉**（丢页面状态/表单）。
  这就是它默认关闭的原因。
- ⌘W 只关**前台窗口的当前标签**。视频在后台标签时，关掉的是别的标签。
- 不抢焦点 = 浏览器在后台时这一级**帮不上忙**，只能靠第 1 级的 pause。

## 后续修订（2026-11-15，v1.2）：上述「绝不抢焦点」策略已废弃

坑 1 的技术事实仍然成立（音频信号不可信），但**产品结论改了**：用户反馈
「勾了这两个开关却什么都没发生」，要求**勾选即在倒计时结束时执行**，
不再把它当「暂停失败后的兜底」。

新的应对方式不是「靠信号判断该不该关」，而是**彻底不看信号**：

| v1.1（本文记录的做法） | v1.2（当前实现） |
|---|---|
| 退出客户端：前面几级全失败才做 | 勾选即 `terminate()`，2 秒未退再加 `forceTerminate()` |
| 关标签：检测到音频 + 浏览器已在前台，绝不抢焦点 | 勾选即枚举运行中的已知浏览器，逐个 `activateAndWait()` 确认到前台后发 ⌘W |
| 条件不满足时静默跳过 | 条件只剩「开关是否勾选」；没浏览器 / 没客户端会在日志里明确写「无需关闭」 |

抢焦点与丢页面状态的代价改由**用户勾选时显式承担**：面板顶部说明、
全屏提醒窗口文案、运行日志三处都会提前告知。所有分支统一走 `finishAll`，
避免「腾讯视频成功停下」这条主路径漏掉附加动作。
